## Current password UI refinement

This section supersedes the earlier hint/control presentation below; historical verification records remain unchanged. Scope is the password section, related messages and regression tests only. No controller, repository, hashing, transaction, schema, credential or XAMPP change.

- Password and Confirm password are stacked vertically at every width and use the available form width. Inline SVG eye buttons sit inside each input on the right, with reserved text padding, type=button, accessible Show/Hide names, visible focus and 44px targets. No icon library/dependency was added. Values and autocomplete=new-password are preserved. Buttons remain hidden without JavaScript.
- The unchanged policy is 12–128 Unicode code points, the 1024-byte UTF-8 guard, no NUL/invalid encoding, no whitespace-only or single-character repetition, and the same 16-entry case-insensitive common-password list. No composition rule, normalization or truncation was added. RegistrationValidator::passwordPolicy supplies public rules/messages to the view through an escaped JSON data attribute; no secrets or user passwords are emitted. PHP passwordError and JavaScript checks share those rules; PHP remains authoritative.
- Exact errors: "Use at least 12 characters.", "Use no more than 128 characters.", "This password is too easy to guess. Try a longer, less predictable password.", and "Avoid repeating the same character for the whole password." Encoding/byte/whitespace-only errors have separate explanations. Confirmation uses "Confirm your password." or "Passwords do not match.".
- With JavaScript, guidance begins on password input/change and remains visible when a rule is unmet. Basic-check success explicitly says "Checked again when you submit."; it does not promise account creation or comprehensive leaked-password screening. Unchanged messages are not repeatedly replaced in live regions. Feedback uses polite atomic status regions and updates aria-invalid/aria-describedby. Reserved helper height reduces shifts, though long messages can wrap at narrow widths.
- Confirmation mismatch is deferred until blur or submission; after that, input/password changes refresh it. A matching confirmation says "Passwords match." without claiming password strength. Server errors appear below the relevant input and remain until editing; editing hides the stale server field error and replaces it with current local guidance. Without JavaScript the static minimum-length hint and server validation remain available. Passwords are still blank after any failed server response.
- No plaintext is logged/persisted, and visibility toggles do not change the value or submit the form. Existing first-submit ordering, CSRF recovery, duplicate email text, session throttling and transaction rules remain unchanged.

Implementation choices: normalize trimmed ASCII email to lowercase (maximum 254 bytes); Full Name is required and maps to the existing display_name column, maximum 100 Unicode characters; role must be client or freelancer. Passwords use Argon2id through password_hash (available in the installed PHP), minimum 12 and maximum 128 Unicode code points/1024 UTF-8 bytes, with NUL/invalid UTF-8/repeated-character and a small obvious-password blocklist rejected. No composition requirement, trimming, normalization or truncation. This is not a comprehensive breached-password service. Password confirmation must match exactly. Argon2id fits the existing VARCHAR(255); the report's bcrypt description needs updating, not the schema. The exact hint "Use at least 12 characters for your password." appears immediately below Password. Password minlength/maxlength HTML attributes were removed because they count UTF-16 units. JavaScript uses Array.from to count code points and TextEncoder to retain the byte safety check. Its submit handler refreshes validity and calls reportValidity for the whole form, including required/email constraints. Server checks remain authoritative without JavaScript. Value changes from autofill are rechecked on submission, even without an input event. Neither layer truncates passwords; combining sequences count as multiple code points, matching PHP.

The documented local blocklist in RegistrationValidator contains 16 case-insensitive obvious choices: numeric sequences beginning 123456789012, several password/qwerty/letmein/welcome variants. The separate repeated-character rule remains. This is deliberately modest, works offline, adds no dependency and is not comprehensive compromised-password detection. Accessible Show/Hide buttons are progressively enabled for each password input, preserve its value and autocomplete=new-password, and update their accessible names. They do not persist/log passwords. Without JavaScript the inputs remain masked and the controls remain hidden.

Optional role-appropriate profile data: About You (bio, both roles, maximum 2000 characters), Company Name (Client only, maximum 100 characters). Empty optional values become NULL. Minimal external JavaScript shows the matching fieldsets; switching to Freelancer clears and disables Company Name. The server independently ignores irrelevant Company Name and all posted portfolio fields. Freelancer profile INSERT writes only user_id and bio; existing portfolio columns remain unchanged and NULL for new registrations. No portfolio controls appear on this form. Future verified Freelancer Profile management may support PDF/JPG/PNG/WEBP files up to 5 MB, stored privately outside htdocs, and optional external links subject to final profile design; it is not implemented here. Unexpected activation/verified/user-ID fields are ignored; role is whitelisted and cannot be Admin.

Without JavaScript, choose a role and press "Update optional fields", located below Create my account; instructions beside the role explain this. This CSRF-protected server-rendered action returns the appropriate optional controls without connecting to the database or creating an account. Non-password values are retained; passwords must be entered again. Changing roles without refreshing optional fields still cannot save irrelevant data. Create my account is the first submit button in DOM order, so Enter invokes creation even without JavaScript. Enhancement changes the fallback to type=button, disables it and hides it. Merely hiding a submit button had allowed it to intercept Enter. Error summaries link to field names rather than repeating field messages; aria-invalid/aria-describedby associate errors, and rejected submissions focus the summary when JavaScript is available. Error responses use the title Registration needs attention. Invalid CSRF still returns 403 before persistence; a whitelist preserves bounded, control-character-filtered, escaped non-password fields, never passwords or unknown fields. Other error recovery uses the same bounds. Assets use a version query to avoid stale cached styles. Existing green two-column desktop styling is retained, with stacked mobile layout and quieter preview notice. Input border #77877b exceeds 3:1 against its white adjacent surfaces.

Duplicate email feedback is exactly "This email is already registered." below Email Address, once per response, for both precheck and database uniqueness violations. This approved wording reveals account existence (account enumeration). A small session-only throttle allows five otherwise-valid, CSRF-checked registration attempts in a rolling ten-minute window, then returns HTTP 429 with Retry-After before opening a connection or hashing. The visible message gives the remaining minutes, rounded up; there is no animated countdown. Duplicate and failed persistence attempts count; invalid forms and role-refresh requests do not. No passwords, email addresses or IP addresses are stored by the throttle. Clearing cookies/new sessions bypass it: this is a local-demo guard, not sufficient distributed/public abuse prevention. Stronger shared server-side abuse protection is required before public deployment; IP/database-backed throttling is explicitly deferred in this task.

Database write test safety: explicitly opt in with php tests/registration-database.php --run-synthetic. Require gighub_dev and the dedicated account, InnoDB tables and expected live columns. Take counts for all 20 application tables, start one outer transaction, and create only random-prefix @example.invalid synthetic accounts. Registration participates through a savepoint when an outer transaction already exists, and owns/commits a transaction for normal standalone requests. Each failure rolls back its own scope. Test a real profile INSERT failure with a test repository subclass that supplies an overlength company name, plus a unique-email race with a subclass that skips the precheck. Always roll back the outer transaction; compare all counts and confirm the synthetic prefix is absent. Never DELETE users, reset tables, alter constraints, or touch gighub_schema_test. Auto-increment gaps may remain. If preflight cannot prove rollback safety, stop before any write.

Normal successful requests commit a pending_verification user and exactly the selected profile, with email_verified_at=NULL and only a password hash. They redirect to a one-time pending notice without retaining account IDs, emails or passwords in the session. Only CSRF/anonymous session metadata and a boolean notice are used. The notice explicitly states no email was sent and SMTP comes next.

Routes: GET/POST public/index.php?route=/register and GET public/index.php?route=/register/pending. Invalid CSRF returns 403, validation/duplicate email returns 422, throttling returns 429, persistence failures return a generic 503. Success uses 303 redirect (POST/redirect/GET). No authenticated session is created. Home/health still do not open a database connection; only a validated, non-throttled account-creation POST obtains the service connection.

References for implementation choices: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html and https://www.php.net/manual/en/function.password-hash.php . CSRF uses random session-bound synchronizer tokens and hash_equals; SameSite cookies alone are insufficient.
